# MarkGleam 搜索意图扩展调研

更新时间：2026-07-30

## 结论

Markdown 应继续作为核心能力、专业用户入口和主要产品心智，不应弱化或改名。

但产品不能要求所有用户先知道 “Markdown” 这个术语。应在 Markdown 主航道之外增加一层以任务结果命名的入口，优先承接：

1. AI 回答转图片；
2. AI 对话转图片；
3. 文字 / 文章转长图。

其中，**AI 回答转图片**与现有产品的能力和用户动作最接近，适合列为下一轮 P0；**文字转长图**需要真正的纯文本模式，适合 P1；**AI 对话转图片**需要双角色输入和对话视觉样式，不能只换页面标题，适合在确认需求后作为 P1 产品扩展。

不建议直接把首页或核心页面改成“文字转图片”。当前搜索结果中，这个词及其英文对应词 `text to image` 的主流意图是 AI 文生图，而不是文字排版成图片。用它做主定位会同时伤害搜索匹配、用户预期和产品辨识度。

## 研究问题

本次调研要回答的不是“认识 Markdown 的人多不多”这一个问题，而是：

- 不知道 Markdown 名称的人，会用什么任务语言寻找现有能力？
- 哪些相邻搜索意图与产品真实能力一致？
- 哪些词虽然看起来流量大，但会带来错误用户？
- 为了承接新意图，哪些页面只需要改表达，哪些必须提供新功能？
- 如何避免为了覆盖同义词而生成低价值的重复页面？

## 已有产品基础

当前工作区已经覆盖 Markdown 转图片、Markdown 长图、Markdown 转 PDF、代码转图片、Mermaid 转图片、公式转图片、GitHub README 转图片和批量转换。

这套能力的共同核心是“把结构化文字内容排版为可分享的视觉成品”，而不是“只处理 `.md` 文件”。普通用户粘贴的 AI 回答往往也包含标题、列表、代码块、表格和公式，只是用户未必知道这些结构叫 Markdown。

因此，问题主要出在**发现路径和输入心智**，不是现有渲染内核方向错误。

## 搜索结果与竞品信号

### 1. “AI 返回内容转图片”同时混有三种意图

2026-07-30 的 Google 结果把这个表达拆成了三类方案：

- 直接截图；
- 将对话或长文本排版成图片；
- 使用 AI 文生图模型生成海报、卡片或信息图。

自然结果的大部分位置被 AI 文生图产品占据，但同时出现了专门的 AI 对话转图产品。这说明用户需求存在，词义却没有稳定下来。

产品含义：

- 不能用宽泛的“文字转图片”或“AI 转图片”作为主页面定位；
- 页面必须用“保留原文并排版”与“根据提示生成新图”做清楚区分；
- “AI 回答转图片”比“文字转图片”更接近本产品，也更少误导。

### 2. “ChatGPT 对话转图片 / AI 对话转图片”已有专门产品

相关结果中出现了：

- ChatGPT 分享和导出浏览器扩展；
- AI 会话导出工具；
- Chat2Image；
- “AI 对话导出为高清图片”的教程内容。

这不是纯粹臆想出来的词，但当前结果数量和用词仍比较分散，尚未形成单一、稳定的品类词。

代表性竞品 [Chat2Image](https://github.com/reckless-huang/gpt2img) 提供：

- 用户输入和 AI 回复两个输入区；
- Markdown 渲染；
- 用户和 AI 头像；
- ChatGPT、DeepSeek、通义千问等 AI 头像；
- 桌面端和手机端布局；
- 手机端自动分页；
- 字号调整；
- 一次下载全部图片。

产品含义：

- “AI 对话转图片”真正对应的是对话编辑器，不是普通 Markdown 页面换标题；
- 竞争点是角色、头像、对话样式和分页，不只是渲染 Markdown；
- 不应为 ChatGPT、Claude、DeepSeek 各复制一个相同页面。品牌只适合出现在正文示例和兼容说明中。

### 3. “文字排版成图片 / 文字转长图”是独立的小工具需求

精确结果中出现了：

- [即时工具：文字生成长图](https://www.67tool.com/work/textToImg)，标题直接强调微博、朋友圈场景；
- [文本工具箱：在线文本转图片](https://txttool.cn/txt2img/)，页面包含工具简介、使用方法和应用场景。

这类用户通常只想粘贴纯文本、保留换行、调整背景和字号，然后得到一张长图。他们不一定需要或理解 Markdown。

产品含义：

- “文字转长图”比“文字转图片”更准确，也更少与 AI 文生图冲突；
- 纯文本输入必须保留自然换行和段落，不能依赖用户学习 Markdown 的空行规则；
- 朋友圈、微博、小红书等是场景修饰词，不应各自复制一套相同工具页。

### 4. Markdown 词本身仍然有价值

Markdown 用户的搜索意图非常明确：他们知道输入格式，也知道期望输出，常见组合包括图片格式、PDF、长图、代码、README、Mermaid 和公式。

这部分用户通常比泛流量用户更接近完成导出，不应为了覆盖非技术用户而牺牲：

- `/markdown-to-image/` 的精确 title 和 H1；
- 编辑器对 Markdown 语法的直接支持；
- 代码高亮、表格、公式、Mermaid 等专业差异；
- README、批量和 PDF 等长尾工具。

当前无法从公开结果可靠推算“认识 Markdown”和“不认识 Markdown”的人数比例。也没有必要先证明某一方占绝对多数：产品可以用两个入口承接同一渲染内核，而不必二选一。

## 关键词与意图分层

### P0：现有能力可高质量承接

| 意图簇 | 建议覆盖表达 | 页面 / 产品动作 |
|---|---|---|
| Markdown 转图 | Markdown 转图片、Markdown to image、Markdown to PNG、md to image、Markdown screenshot | 保留现有 `/markdown-to-image/`，同义词写入自然文案，不复制 URL |
| AI 单条回答转图 | AI 回答转图片、AI 回复转图片、AI 生成内容转图片、ChatGPT 内容转图片 | 新增一个任务型入口；编辑器标为“AI 回答”，底层继续支持 Markdown |
| Markdown 长图 | Markdown 转长图、Markdown long image、长 Markdown 转图片 | 保留现有 `/markdown-long-image/` |

### P1：需要真实产品差异后再建可索引页

| 意图簇 | 建议覆盖表达 | 必要功能 |
|---|---|---|
| 纯文字长图 | 文字转长图、文本转长图、文章转长图、文字排版成图片 | 纯文本输入、保留换行、段落间距、长图 / 分片导出 |
| AI 对话转图 | AI 对话转图片、聊天记录转图片、ChatGPT 对话转图片 | 用户 / AI 双角色输入、对话样式、角色名或头像、移动端分片 |
| 内容卡片 | 文字卡片生成器、金句卡片、quote card generator | 卡片模板、作者 / 来源、短内容版式、固定比例预设 |

### P2：产品进入内容再利用后考虑

| 意图簇 | 机会 | 为什么不立即做 |
|---|---|---|
| 文章转轮播图 | 小红书图文、LinkedIn carousel、blog to carousel | 需要自动分段、多页排序和跨页样式，不是当前单画布的自然延伸 |
| 网页 / 链接转图 | URL to image、网页长截图 | 需要远程抓取服务，会引入 CORS、隐私、滥用和运行成本 |
| AI 自动美化 | AI 排版、内容转海报、内容生成信息图 | 需要模型调用和不确定生成结果，会改变本地优先的产品边界 |

### 明确不抢

- `文字转图片`、`text to image`：主流意图是 AI 文生图，除非搭配“排版、长图、卡片”等限定词；
- `AI 图片生成器`、`文生图`：产品能力不匹配；
- `图片转文字`、OCR：方向相反；
- `网页截图`、`网站转图片`：当前没有远程页面渲染能力；
- 为 PNG、JPG、WebP、ChatGPT、Claude、DeepSeek 分别创建功能完全相同的页面。

## 产品策略

### 保持双层心智

产品不需要在“Markdown 工具”和“普通用户工具”之间二选一。

推荐的信息架构是：

1. 品牌层：把结构化内容做成可分享的视觉作品；
2. 任务层：AI 回答、文字长图、Markdown、代码、图表、公式；
3. 能力层：主题、画布、分页、导出格式、本地处理。

首页仍然保留 Markdown 的明确露出，但在首屏或转换类型导航里增加“AI 回答”入口。非技术用户先看到任务，专业用户仍能直接看到格式。

### P0 页面：AI 回答转图片

建议路由：

- 中文：`/ai-response-to-image/`
- 英文：`/en/ai-response-to-image/`

建议中文核心文案：

- Title：`AI 回答转图片：把 ChatGPT 等回复排版成长图 · MarkGleam`
- H1：`AI 回答转图片`
- 输入区：`粘贴 AI 回答`
- 辅助说明：`直接粘贴回答即可。标题、列表、代码块、表格和公式会按原结构排版。`
- 区分说明：`这里不会根据提示词生成新图片，而是保留原文内容并重新排版。`

最低产品差异：

- 页面和编辑器不要求用户先理解 Markdown；
- 默认使用适合分享的自适应长画布；
- 输入示例是一段真实可渲染的 AI 风格回答；
- 标题、列表、代码、表格和公式直接工作；
- 页面正文明确兼容 ChatGPT、Claude、Gemini、DeepSeek 等复制出的文本，但不冒充这些品牌的官方工具。

不应创建：

- `/chatgpt-to-image/`
- `/claude-to-image/`
- `/deepseek-to-image/`

除非未来不同来源有真实、可验证的专属导入能力。

### P1 功能：纯文字长图

建议先新增 `text` 输入模式，再创建 `/text-to-long-image/`。

最低产品差异：

- 单换行得到可见换行；
- 连续空行保留段落间距；
- 不把 `#`、`*`、`_` 等普通字符强制解释为语法；
- 支持 TXT 导入；
- 默认自适应高度；
- 超长内容可按语义块分片并下载 ZIP。

### P1 功能：AI 对话转图片

只有完成下列能力后，才创建 `/ai-conversation-to-image/`：

- 至少一组“用户提问 / AI 回答”输入；
- 可添加多轮；
- 明确区分两个角色；
- 移动端聊天样式；
- 对长回答进行内容块级分片；
- 支持一次下载全部分片；
- 头像和品牌图标使用通用、自定义方案，避免默认盗用第三方商标。

## SEO 边界

Google 的 [Spam policies](https://developers.google.com/search/docs/essentials/spam-policies#doorway-abuse) 将“为相似查询创建大量实质相同页面，并把用户导向同一个最终工具”列为 doorway abuse。

因此，本项目继续遵循“一种真实工具状态，一个可索引页面”的原则：

- 同义词放在同一页面的自然文案、FAQ、结构化数据和内链中；
- 只有输入方式、预设、渲染结果或操作流程真实不同，才新增 URL；
- 所有可索引页面打开后应直接进入对应工具状态，而不是先读一篇 SEO 文章再跳转；
- 不在页面底部堆积关键词列表。

## 验证计划

当前公开数据只能证明意图存在和结果页结构，不能提供可靠搜索量。Google Trends 对这些低频、中文长尾组合没有在本次调研中返回可用的稳定数据，因此不写伪精确月搜索量。

更可靠的验证方式是发布后使用第一方数据。

### 发布前

- 为 P0 页面提供独立静态 HTML、title、description、canonical、hreflang、结构化数据和 sitemap；
- 记录入口页面、工具类型、首次输入和成功导出；
- 所有分析事件只记录动作和页面，不记录用户粘贴的正文。

### 发布后 28 天

在 Google Search Console 和百度搜索资源平台按“查询 × 页面”查看：

- 曝光查询是否落在 AI 回答排版，而不是 AI 文生图；
- `/ai-response-to-image/` 是否获得非 Markdown 查询；
- 搜索点击后的首次输入率；
- 首次输入后的成功导出率；
- 新入口是否蚕食 `/markdown-to-image/`，还是带来新增查询。

### 决策规则

- 有相关曝光但点击率显著低于站点同位置页面：先改 title / description，不先扩功能；
- 有点击和输入但导出率低：检查粘贴格式、默认画布和移动端结果；
- “对话、多轮、头像、聊天样式”等站内反馈或查询持续出现：进入 AI 对话模式开发；
- “纯文本换行丢失、不会 Markdown、文章长图”等问题持续出现：提升纯文字长图优先级；
- 查询仍主要是文生图：收紧页面文案，不扩展到泛 `text to image`。

## 推荐执行顺序

1. 发布并稳定当前 Markdown、代码、图表和公式工具页；
2. 增加一个真正可直接使用的“AI 回答转图片”入口，不改变 Markdown 主页面定位；
3. 补齐匿名、无正文内容的漏斗事件；
4. 累积 28 天搜索与导出数据；
5. 在“纯文字长图”和“AI 对话转图片”中选择数据更强的一项实现；
6. 只有当多页内容复用信号明确时，再考虑小红书 / LinkedIn 轮播图。

## 最终判断

用户的担心是成立的：确实存在“不知道 Markdown 名称，但需要把 AI 回答或文字内容做成图片”的人群，而且现有搜索结果中已经有专门产品承接他们。

但这不意味着 Markdown 应从产品主调性中退场。更合理的做法是：

- **保留 Markdown 作为清晰、有效的专业入口；**
- **增加 AI 回答、文字长图等结果导向入口；**
- **让用户无需知道 Markdown，也能在同一内核上完成任务；**
- **只为真实不同的工具状态创建页面，不为同义词批量造页。**

这既能接住非技术用户，也不会稀释现有产品的专业辨识度。
